# Introduction

Lithos is Roblox infrastructure-as-code. It keeps config, persisted state,
and the live Roblox API in sync so deploys stay reviewable and repeatable.

If you have used Terraform, Pulumi, or AWS CDK before, the model will feel
familiar. If you have not, this page covers the core model you need.

<DocsIntroShowcase />

## The three things Lithos owns

1. **A configuration file** (`lithos.yml` or `lithos.json`) — the source of
  truth. What you want to exist.
2. **A state file** (`.lithos-state.yml`, local or remote) — the current
  graph Lithos believes exists, plus a short deployment history.
3. **A live API** (Roblox + Open Cloud) — what actually exists *right now*.

Every command is a function of those three inputs. `deploy` reconciles them
in that order: read config, read state, verify state against the live API,
plan a diff, apply it, write new state.

<Callout type="info">
  **State is what Lithos thinks exists. The live API is what actually
  exists.** When they disagree, Lithos treats it as drift and reconciles
  before destructive work.
</Callout>

<Callout type="info">
  State also stores recent deployment checkpoints. `lithos undo` rolls back
  toward those snapshots.
</Callout>

## Why it matters

Lithos moves the metadata that usually lives in Studio and Creator Hub into
source control: place names, server settings, products, passes, badges,
thumbnails, social links, voice settings, and more.

- Every deploy is **reviewable**: a plan preview shows exactly which fields
  on which resources will change, before any byte hits Roblox.
- Every rollback is **explicit**: revert the YAML and redeploy, or use
  `lithos undo` to drive Roblox back toward the last checkpoint.
- Every environment is **reproducible**: `dev` and `prod` come from the same
  config with declarative overrides, not parallel checklists.
- Every CI pipeline is **predictable**: one binary, one state file, and a
  small set of secrets.

## What Lithos is not

- **Not** a replacement for [Rojo](https://rojo.space/). Rojo turns Lua
  source files into a `.rbxlx`. Lithos uploads that `.rbxlx` to a place and
  configures everything around it. They are complementary tools.
- **Not** a runtime. Lithos runs on your machine or in CI. It does not run
  inside Roblox.
- **Not** an SDK. There is no Lithos library you call from your game code.

## The shortest possible example

```yaml filename="lithos.yml"
target:
  experience:
    configuration:
      genre: building
    places:
      start:
        file: game.rbxlx
        configuration:
          name: My Experience
```

```text
$ lithos deploy
```

On first deploy, Lithos creates the experience, uploads `game.rbxlx`, and
writes the resulting IDs to state. Run the same command again and it noops
unless the inputs changed.

Change the place name and redeploy, and Lithos updates exactly that field.
