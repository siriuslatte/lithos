CLI Commands

CLI reference

Every Lithos workflow is one of six subcommands. This page is the working reference; for the full machine-readable surface, run lithos --help or lithos <subcommand> --help.

CommandPurpose
deployReconcile state with config and apply the diff.
diffPrint the diff without applying it.
undoRestore the last recorded checkpoint for an environment.
outputsPrint the outputs of the last deploy as JSON, YAML, or importable modules.
destroyRemove every resource Lithos manages for an environment.
importAdopt an existing experience into a Lithos project.

All commands accept a positional PROJECT argument. If omitted, Lithos looks for lithos.yml, then lithos.yaml, then the legacy mantle.yml and mantle.yaml in the current directory; if provided as a directory, Lithos looks inside it; if provided as a file, Lithos uses that file directly. See Configuration → Config file resolution.

deploy

$ lithos deploy [PROJECT] --environment <label> [flags]

The default workflow. deploy runs the pipeline described in The resource graph: load config and state, reconcile state against the live Roblox API, build the desired graph, run preflight diagnostics, render a plan preview, prompt for confirmation, checkpoint the current environment state, and apply the diff in dependency order.

Live reconciliation

Before computing any diff, deploy asks Roblox to confirm that the resources persisted in state still exist. Each resource is classified as verified, missing, skipped, or unknown. Resources confirmed missing are dropped from the previous-state graph so the next plan re-creates them rather than producing a broken update against a deleted asset. Resources whose verification is inconclusive (permission denied, network error) are preserved unchanged so behavior degrades safely.

Verified resource types: experiences, places, game passes, developer products. Sub-resources (configurations, thumbnails, ordering, place files, badges, image/audio assets, asset aliases, social links, spatial voice, notifications) are skipped intentionally — they have no cheap, authoritative existence endpoint, and their drift is implied by the verification of their parent.

Plan preview and confirmation

Before any creates, updates, or deletes hit Roblox, deploy renders a plan preview: a color-coded, structured view of every operation, grouped by kind. Risky resources (developer products, game passes, badges) get field-level summaries — price, name, description — so you can confirm an "update" really is just a price change before approving it. Destructive operations on developer products, game passes, badges, notifications, experiences, and places are flagged with an explicit warning marker.

When stdout is an interactive terminal, deploy prompts to confirm before applying. Press y or Enter to apply; anything else cancels. In non-interactive contexts (CI, piped output) deploy auto-approves after printing a plain summary, so existing scripts continue to work.

Preflight diagnostics and checkpoints

Before approval, deploy runs a preflight pass over the plan and auth context. This catches the common Roblox failures that are otherwise vague at runtime: missing Open Cloud keys, missing universe-places.write, API keys that do not cover the target universe, unsupported group/public/friends combinations, and place files that are close to Roblox's size limits.

If any preflight diagnostic is blocking, deploy stops before mutating anything. If preflight passes, Lithos records a checkpoint of the last known good graph so lithos undo can roll the environment back toward that snapshot later.

Useful flags

FlagEffect
--environment <label> / -eRequired. Which environment block to apply.
--yes / -ySkip the confirmation prompt and apply immediately.
--no-previewSkip the preview entirely. Implies --yes.
--plain-previewRender a plain (non-colored) summary. Useful in CI log viewers without ANSI support.
--allow-purchasesAllow paid-asset operations (developer products, etc.) without an extra confirm.
⚠️

--no-preview is a footgun outside of well-tested pipelines. The preview is the only thing standing between you and an unintended delete.

diff

$ lithos diff [PROJECT] --environment <label> [--live]

Print the diff between persisted state and project configuration. Useful in pull-request CI to comment "what would this PR do?" without applying.

By default diff is offline — it does not contact Roblox. Pass --live to run the same reconciliation pass that deploy runs, surface drift, and diff against the reconciled previous-state graph:

$ lithos diff --environment dev --live

Use --live when you suspect drift; use plain diff when you just want to know what your YAML changes would do.

undo

$ lithos undo [PROJECT] --environment <label> [flags]

Best-effort rollback to the most recent checkpoint Lithos recorded for an environment. undo does not read old YAML or Git history. Instead it:

  1. Loads the baseline snapshot stored before the last deploy or undo.
  2. Imports the live Roblox experience so rollback plans against reality, not stale state.
  3. Runs the same preflight diagnostics and plan preview as deploy.
  4. Applies the diff back toward that snapshot and records the result.

Use the same preview flags as deploy: --yes, --no-preview, and --plain-preview. --allow-purchases is also supported in case rollback needs to recreate a paid resource.

Roblox deploys are not transactional. undo is therefore best-effort: it reconciles live state and then drives resources back toward the last checkpoint Lithos recorded.

outputs

$ lithos outputs [PROJECT] --environment <label> [--output <file>] [--format <format>] [--roblox-ts]

Print the outputs of the last deploy. Stdout still defaults to JSON for CI and piping, but when --output ends in .lua or .luau, Lithos infers a game-ready Luau module from the file extension. You can also set --format explicitly to json, yaml, yml, lua, or luau.

Pass --roblox-ts when writing a Luau module to a file and Lithos will also write a matching .d.ts sidecar next to it for typed roblox-ts imports.

You can also move those defaults into your project config so lithos outputs does the file generation with no extra flags. Lithos reads a top-level outputs block (or the alias codegen) and uses it as the default output request; explicit CLI flags still win.

lithos.yml
outputs:
  writeDir: src/shared/generated
  outputName: lithosOutputs
  format: luau
  robloxTs: true

The codegen alias also accepts Asphalt-style snake_case names:

lithos.yml
codegen:
  write_dir: src/shared/generated
  output_name: lithosOutputs
  format: luau
  typescript: true

With either config, this is enough:

$ lithos outputs --environment dev

When writeDir + outputName omit an extension, Lithos adds one from format. If robloxTs / typescript is enabled and format is omitted, Lithos defaults to .luau so the .d.ts sidecar can be generated.

After deploying the getting-started example (opens in a new tab), running outputs with the default JSON format looks like:

{
  "experience_singleton": {
    "experience": {
      "assetId": 3296599132,
      "startPlaceId": 8667346609
    }
  },
  "place_start": {
    "place": { "assetId": 8667346609 }
  },
  "placeFile_start": {
    "placeFile": { "version": 2 }
  }
}

Generate a Luau module when you want game code to require the outputs directly instead of templating JSON into source later:

$ lithos outputs --environment dev --output src/shared/generated/lithosOutputs.luau
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local outputs = require(ReplicatedStorage.shared.generated.lithosOutputs)

local startPlaceId = outputs.experience_singleton.experience.startPlaceId
local placeVersion = outputs.placeFile_start.placeFile.version

For roblox-ts, keep the generated Luau module as the runtime source and add --roblox-ts so Lithos also writes lithosOutputs.d.ts beside it:

$ lithos outputs --environment dev --output src/shared/generated/lithosOutputs.luau --roblox-ts
import outputs from "shared/generated/lithosOutputs";
 
const startPlaceId = outputs.experience_singleton.experience.startPlaceId;
const placeVersion = outputs.placeFile_start.placeFile.version;

If the file path comes from outputs.path or outputs.writeDir + outputs.outputName, the same .d.ts sidecar behavior applies without passing --roblox-ts on the command line.

destroy

$ lithos destroy [PROJECT] --environment <label> [--yes]

Remove every resource Lithos manages for an environment. Lithos cannot hard-delete most Roblox asset types, so in practice this archives them and clears them from state.

destroy is a deploy whose diff is "delete everything." It runs the same plan preview, the same confirmation prompt, and the same dependency ordering. Use the same flags.

🚫

destroy is irreversible from Lithos's point of view: state is wiped. The Roblox-side assets are archived, not gone, but recovering them and reattaching to a fresh state requires import (experimental).

import

$ lithos import [PROJECT] --environment <label> --target-id <experience-id>

Adopt an existing Roblox experience into a Lithos project. This is for the case where you already have a published experience and want to start managing it with Lithos.

⚠️

import is experimental. It does not match every existing resource to a configured one — most resources will be re-created on the next deploy. Always test on a staging environment before importing a production experience.

A safer pattern: build a Lithos config that mirrors your production setup, deploy it as a staging environment to verify the diff is empty, and only then point import at production.

Exit codes

CodeMeaning
0Success. Includes the case "nothing to do."
1A user-facing failure. Bad config, auth failure, apply failure, conflicting state, etc. The error message names the cause.
2The command was cancelled at the preview / confirmation step.

In CI, treat any non-zero exit as fatal.
